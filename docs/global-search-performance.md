# 全局消息搜索性能验证（2026-11-10）

全局搜索继续使用 PostgreSQL，按当前成员资格过滤，以 `strpos(lower(content),lower(query))` 精确判断字面子串。迁移 `000031` 增加不依赖扩展的 Unicode 1/2/3 字符词元 GIN 表达式索引，覆盖单字中文、双字词、emoji、标点和 `%`、`_`、反斜杠。查询词使用最长宽度的词元筛选候选，精确复核消除词元顺序或重复造成的假阳性。

部分表达式索引的选择率在本机 PostgreSQL 上仍可能按默认 0.5% 估算，即使 `pg_stats` 已记录该词元接近全表都有。全局搜索显式读取此索引的元素频率：查询全部词元的最低频率达到 20% 时走成员范围内的精确查询，否则使用 GIN 候选查询。频率只决定成本路径，两条路径保留相同的权限、撤回、字面匹配和游标条件；统计缺失时使用 GIN 路径，不影响结果。建索引后执行 `ANALYZE messages`，之后由正常 autovacuum/analyze 刷新。

查询先选出 `limit+1` 个候选 ID（接口 limit 最大 50），再读取图文块、附件、引用、会话信息。成员数按当前页不同的会话计算一次。分页使用 `(created_at,id)` 复合游标，不使用深 OFFSET 或仅在会话内有效的 seq。每次查询使用实际参数生成计划，避免不同热度关键词共用不适合的通用计划。

前端保留显式提交，增加相同关键词在途提交去重、AbortController 和版本校验。关闭、重搜、账号变化及卸载会取消旧搜索；分页绑定已提交关键词，避免编辑输入后把新词与旧游标混用。

## 测试规模与方法

隔离测试 schema，创建 10,000 个会话（80% 私聊、20% 群聊）、300,000 条新增消息。正文包含中文、英文、不同 md5 文本，以及稀有词、字面符号和 emoji。广范围用户参与 5,000 个会话、可见 150,000 条新增消息；小范围用户参与 5 个会话、可见 150 条新增消息。背景消息属于其他会话；另有 fixture 历史数据用于权限与旧消息验证。该数据不代表真实群人数分布或所有长文本比例。

每个关键词对比原 `strpos` 查询与新查询的 ID、排序、has_more、下一页首个 ID。原基准只获取候选 ID，新查询还包含消息详情及会话元数据；两者都能使用迁移后的辅助索引，所以对旧方案的比较较保守。每组各运行三次 `EXPLAIN (ANALYZE,BUFFERS,FORMAT JSON)`，表中为数据库执行时间中位数，不含网络、前端渲染与规划时间。不是 p95/p99 或并发吞吐承诺；本轮同时运行了其他独立 schema 的后端回归，时间有负载波动。

| 参与范围 | 关键词 | 原候选查询 ms | 新完整查询 ms |
| --- | --- | ---: | ---: |
| 5,000 会话 | 的（高频） | 104.387 | 103.913 |
| 5,000 会话 | 预算（稀有） | 530.509 | 9.663 |
| 5,000 会话 | needle-unique | 588.972 | 5.224 |
| 5,000 会话 | 不存在的编号 | 575.119 | 1.959 |
| 5,000 会话 | %_ | 18.000 | 27.066 |
| 5,000 会话 | 😀 | 12.718 | 27.027 |
| 5 会话 | 的 | 0.985 | 2.662 |
| 5 会话 | 预算 | 0.739 | 2.329 |
| 5 会话 | needle-unique | 0.804 | 2.998 |
| 5 会话 | 不存在的编号 | 0.919 | 1.997 |
| 5 会话 | %_ | 0.785 | 10.148 |
| 5 会话 | 😀 | 0.569 | 6.613 |

稀有词与无匹配查询有显著收益；高频词保留原有成本路径。少量可见消息和部分符号查询存在固定统计读取、候选及详情组装开销，因此没有宣称每个关键词都比旧候选查询更快。

GIN 索引约 87.8 MB；会话时间索引约 17.7 MB；全局时间索引约 12.2 MB。正式样本中新增索引构建约 4 分 3 秒。128 条每条 4,000 字符的长文本批次，保留新消息索引时约 6.20 秒，事务内移除新消息索引时约 50ms；每次都回滚，未保留测试数据。这是极端长文本同步写入的成本提示，正常短消息和真实并发写吞吐仍需按部署环境另测。

## 复现

使用独立测试 PostgreSQL，设置 `IM_TEST_DATABASE_URL`；测试自动创建和清理 schema，不使用业务数据：

```powershell
Set-Location backend
$env:IM_TEST_SEARCH_PERFORMANCE='1'
go test -v ./internal/logic -run '^TestGlobalSearchPerformance$' -count=1 -timeout 600s
```

默认 300,000 条消息；诊断时可设置 `IM_TEST_SEARCH_MESSAGES=30000`（允许 30,000..1,000,000）。未显式开启性能测试时正常回归跳过该规模装载。功能测试另覆盖短 Unicode、字面标点、同时间 ID 排序、旧消息、权限变更、撤回和统计缺失；前端测试覆盖取消、旧响应、重复提交、分页重试及账号变化。

迁移执行器逐项在事务内运行，因此普通 CREATE INDEX 会阻塞写入，大库需要安排维护窗口。若要在线构建，需独立设计事务外的 CREATE INDEX CONCURRENTLY 流程，不可直接在当前迁移里添加 CONCURRENTLY。索引增加了存储、构建和写入成本；千万级消息、冷缓存、多个并发搜索以及接近 4,000 字的消息分布仍需独立容量验证。
